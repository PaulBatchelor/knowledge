@10:51 precision counters #timelog:00:30:28
#! dz $
I've decided it's worth the energy to think about high
precision counters. A counter is used to store the current
playback position of audio, in units of samples. Every time a
sample of audio is computed,
this counter is incremented by some amount. The tricky part
is that the counter can be fractional, not just an integer
value. For sound file playback, these numbers can get rather
large, and I'm hesistant to represent this as a floating
point value. As numbers get larger, the number of steps between
integers gets smaller. That means that as an audio file progresses
through a file, the scrubbing will start to degrade.
---
Instead of using a float or double for the counter, use
a combination of an integer and a fractional component. The
fractional component is some value between 0 and 1. And the
integer component is some non-negative value. The idea is
that incrementing the counter (positive or negative direction)
will carefully process the fractional and integer parts
individually such that the floating point arithmetic is always
bounded to reasonably small values.
---
This precision counter data depends on the ability to reliably
extract fractional/integer components from a floating point
value. This can be done with the {\tt modf} function in C.
---
A precision counter $P$ is updated by incrementing it by some
real value $R$ (a double value), which can be positive or
negative. This value is added to the current fractional
value $P_a$, and the integer/fractional components are
extracted: $(R_i, R_f) = M(R + P_a)$, and these values are
then used to update the integer/fractional components of
$P$ $P_i$ and $P_a$. $R_f$ can be negative, so that edge
case needs to be handled.
---
When applying $(R_i, R_f)$ to $(P_i, P_a)$, one of three
edge cases needs to be addressed. The first two edge cases
look at the sign of $R_f$. In the simplest case,
$P_i \leftarrow P_i + R_i$ and $P_a \leftarrow R_f$ when $R_f$
is non-negative. When $R_f$ is negative, it gets converted
to a positive value by subtracting 1 from the integer component
and adding it to the fractional component, making
$P_i \leftarrow P_i + R_i - 1$ and $P_a \leftarrow R_f + 1$.
$P$ needs to be non-negative, so a final condition sets $P = 0$
if the result ends up being non-negative.

@11:28 audio interpolation and playback #timelog:00:21:20
#! dz thoughts/projects/scrubant
It's turning out to be a thinky late morning. So, I'm writing
down my thoughts on audio playback, which is the extent
of what I have in mind for the initial work for scrubant.
---
Audio playback loads a single audio file (via libsndfile),
and reads through the file at some playback rate, reprented
by an increment amount. Normal playback has an increment of
one sample at a time. This can go up or down to change
speed. When it is negative, reading goes backwards.
---
Linear interpolation will be used to determine the sample.
The counter will be set up in such a way so that the fractional
component can be used as an interpolation coefficient for the
$n + 1$th sample. (For going backwards, the math should work out.
Interpolating backwards would normally mean interpolating between
the $n$th sample and the $(n - 1)$ sample. But, the counter
does some math to keep the fractional bit between 0 and 1, so
the relationship is still preserved).
---
The inner loop will call a function that gets two contiguous
samples, and interpolates them. That getter function will
determine when to do a disk read. Then, the read playhead will
be increased. Some other function will handle the math for
that.
---
My solution for buffering is to choose a big buffer, and to
always read buffers in such a way that a target sample is
the midpoint. This allows the playhead to read before and
after the sample. I'm choosing a big buffer size, about 5 seconds
of 44.1kHz audio, rounded up to the nearest power of 2. When
this value gets used for stereo audio, and is halved for forward/backward
playback, you get about 1.49 seconds or so of audio? At 8x speed,
it'll probably reading once every 180ms. I'm hoping that'll be
fast enough? I can revisit.
---
To actually get things into JACK, the interleaved samples need
to be written to separate left and right buffers.
